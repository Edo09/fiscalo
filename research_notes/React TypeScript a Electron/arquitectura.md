# Arquitectura oficial de Electron

**Fecha de revisión:** 9 de octubre de 2026. Se consultó la documentación oficial `latest` de Electron; esta documentación es continua, por lo que conviene revisar de nuevo las APIs concretas al fijar la versión del runtime.

## ¿Cómo alojar la aplicación React + TypeScript en Electron y separar main, renderer y preload?

### Takeaway

No hace falta reescribir React: Vite sigue compilando los HTML y bundles del renderer. Electron añade el proceso `main` para ciclo de vida y funciones del sistema; cada `BrowserWindow` carga un renderer web aislado. Un `preload` pequeño y tipado conecta ambos cuando hace falta una capacidad de escritorio.

### Cited Findings

- Electron define un único proceso `main`, que corre en Node.js y crea/administra ventanas, y procesos `renderer` separados por ventana, donde la interfaz debe comportarse como una aplicación web. El renderer no debe importar directamente Node; continúa usando un bundler web como Vite. — [Electron Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model)
- El `preload` se ejecuta antes de la página, tiene un conjunto limitado de APIs privilegiadas y puede exponer una API propia con `contextBridge`. Con aislamiento activo, asignar `window.foo` directamente desde preload no publica ese objeto en el mundo de la página. — [Electron Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model); [Context Isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation)
- Electron recomienda evitar `file://` para cargar páginas locales y usar un protocolo propio, porque `file://` tiene privilegios amplios de archivos. El protocolo propio se registra como privilegiado antes de `app.ready`; `protocol.handle` permite resolver las solicitudes a los recursos locales. — [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security); [Electron protocol API](https://www.electronjs.org/docs/latest/api/protocol/)
- Un protocolo personalizado debe registrarse con el privilegio `standard` para resolver recursos relativos y habilitar APIs de almacenamiento web como `localStorage`; sin él, esas APIs están deshabilitadas para esquemas no estándar. — [Electron protocol API](https://www.electronjs.org/docs/latest/api/protocol/)
- Electron no prescribe una integración particular de Vite en estas guías. Sus tutoriales describen cómo crear la ventana/cargar HTML y dejan el empaquetado y pipeline del frontend a la aplicación. — [Building Your First App](https://www.electronjs.org/docs/latest/tutorial/tutorial-first-app); [Packaging Your Application](https://www.electronjs.org/docs/latest/tutorial/tutorial-packaging)

### Inferences

- El proyecto ya tiene dos entradas Vite, `index.html` y `pos.html`; su build cambia la primera a `app.html` y conserva `pos.html`. Por eso la adaptación de menor impacto puede conservar ambos renderers web y hacer que `main` abra una ventana con `app://bundle/app.html` o `app://bundle/pos.html`, sirviendo solo archivos incluidos en `dist`. No se necesita convertir las vistas React a componentes nativos. Evidencia local: [package.json](../../package.json), [vite.config.ts](../../vite.config.ts), [index.html](../../index.html), [pos.html](../../pos.html).
- Organización inicial sugerida: `electron/main.ts` para `app`, `BrowserWindow`, protocolo y handlers; `electron/preload.ts` para una superficie `window.desktop`; y un archivo de tipos globales para esa superficie. La configuración de Vite compila el renderer existente y un paso aparte compila main/preload para el runtime Electron. Mantener estas compilaciones diferenciadas evita que Electron/Node termine incluido en el bundle web.
- La app actual obtiene sus datos de una API: el build web usa `VITE_API_BASE_URL` y el proxy de Vite está definido solo para desarrollo. El ejecutable instalado no tendrá el proxy de Vite; deberá usar la API remota por HTTPS, con un origen de producción configurado explícitamente. No incluir `API_KEY` ni otra clave de servidor en variables `VITE_` o en el renderer compilado, porque el bundle del cliente se distribuye al usuario. Evidencia local: [vite.config.ts](../../vite.config.ts), [.env.example](../../.env.example).
- Una aplicación de facturación puede seguir siendo cliente de una API remota; Electron por sí solo no convierte al backend ni a la base de datos en locales. Mantener el backend como autoridad para emisión, rangos e-NCF, estado DGII, permisos y persistencia evita que varias instalaciones creen estados fiscales independientes. El esquema local incluye facturas, XML firmado, estado DGII y secuencias, y la API HTTP ya señala que una escritura puede completarse en servidor aunque el cliente agote su timeout. Evidencia local: [src/api/http.ts](../../src/api/http.ts), [src/db/schema.ts](../../src/db/schema.ts).

### Gaps

- La documentación oficial no decide cuál empaquetador/build plugin de Vite debe elegirse para este repo. Antes de implementarlo hay que fijar versiones compatibles de Electron y del empaquetador y hacer una prueba mínima de build, ejecución en desarrollo y carga de los dos HTML.
- La inspección se limitó al frontend. No se puede confirmar qué servidor firma el XML ni quién custodia actualmente el certificado digital DGII; revisar el backend antes de diseñar almacenamiento local de certificados.

## ¿Cómo deben conectarse renderer, preload y main por IPC, y qué protecciones requiere el renderer?

### Takeaway

El renderer debería llamar funciones específicas publicadas por preload, que a su vez usen IPC asíncrono para pedir una operación concreta al main. Mantener `nodeIntegration: false`, `contextIsolation: true` y sandbox activo; validar el origen del emisor IPC, limitar navegación/ventanas externas y aplicar CSP restrictiva.

### Cited Findings

- La recomendación de seguridad de Electron incluye: cargar contenido seguro, aislar contexto, habilitar sandbox, mantener `webSecurity`, definir CSP restrictiva, limitar navegación y creación de ventanas, validar el `sender` de IPC, usar una versión actualizada de Electron y no exponer APIs Electron a contenido no confiable. — [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security)
- En `WebPreferences`, `nodeIntegration` es `false` por defecto, `sandbox` es `true` desde Electron 20 y `contextIsolation` es `true` desde Electron 12. Habilitar `nodeIntegration` deshabilita sandbox. — [WebPreferences](https://www.electronjs.org/docs/latest/api/structures/web-preferences); [Process Sandboxing](https://www.electronjs.org/docs/latest/tutorial/sandbox); [Context Isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation)
- Para operaciones de ida y vuelta, `ipcRenderer.invoke` con `ipcMain.handle` devuelve una promesa. La guía de Electron recomienda exponer una función de preload por operación y explícitamente desaconseja exponer el módulo `ipcRenderer` entero o sus métodos crudos. Desde Electron 29 tampoco es posible pasar `ipcRenderer` completo mediante `contextBridge`. — [Electron IPC](https://www.electronjs.org/docs/latest/tutorial/ipc); [ipcRenderer API](https://www.electronjs.org/docs/latest/api/ipc-renderer); [Context Isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation)
- Electron usa Structured Clone para serializar IPC: funciones, promesas, símbolos, objetos DOM y varios objetos nativos no se pueden pasar como payload. Se deben enviar datos simples serializables y validar tipos/valores en el main. — [ipcRenderer API](https://www.electronjs.org/docs/latest/api/ipc-renderer); [Electron IPC](https://www.electronjs.org/docs/latest/tutorial/ipc)
- Hay que validar `event.senderFrame`/origen en cada handler IPC; iframes y otras ventanas también pueden enviar mensajes. Electron recomienda bloquear navegación no permitida y denegar nuevas ventanas no esperadas con `setWindowOpenHandler`; `shell.openExternal` solo debe recibir destinos confiables. — [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security); [Opening Windows from the Renderer](https://www.electronjs.org/docs/latest/api/window-open)
- La CSP agrega defensa contra XSS y carga de recursos no autorizados. Electron prefiere enviarla como header HTTP; también documenta meta tag para casos donde no se puede establecer el header (como carga `file://`). — [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security)

### Inferences

- API preload inicial razonable: métodos de propósito específico como `getPrinterList`, `printReceipt`, `saveXml`, `openExternalLink` o `getAppVersion`; que no exponga `fs`, `shell`, `ipcRenderer`, rutas arbitrarias ni un `invoke(channel, ...args)` genérico. Cada handler valida que el `sender` venga del protocolo local esperado, valida argumentos y limita la operación y los archivos/destinos alcanzables.
- El frontend actual usa `window.open`, `window.print`, PDFs/XML por Blob y un flujo de impresión de recibos HTML con CSS `@page`. La política de negar ventanas emergentes debe contemplar estos flujos intencionales: convertir la impresión/descarga a operaciones controladas por main o admitir únicamente las ventanas/blob necesarias con reglas claras. Electron expone `webContents.print` con opciones de impresora, tamaño de papel, márgenes y resultado de impresión; se debe comprobar si respeta el tamaño 80 mm actual antes de reemplazar el flujo. Evidencia local: [src/lib/printHtml.ts](../../src/lib/printHtml.ts), [src/lib/file.ts](../../src/lib/file.ts); API: [webContents.print](https://www.electronjs.org/docs/latest/api/web-contents/#contentsprintoptions-callback).
- CSP propuesta para producción: política servida en el header de la app local; permitir scripts solo desde el origen de la app; `connect-src` solo al origen HTTPS de la API; `img-src` con `data:`/`blob:` solo si los recursos actuales los necesitan; y `style-src`/`font-src` solo con recursos locales o los dominios de Google Fonts usados hoy. Conviene empaquetar las fuentes para reducir terceros. Revisar los estilos inline existentes antes de fijar la directiva; no agregar `unsafe-eval` o comodines como arreglo general. Evidencia del frontend: [index.html](../../index.html), [pos.html](../../pos.html), [src/lib/file.ts](../../src/lib/file.ts).
- Ambos HTML actuales enlazan a Google Fonts y no contienen CSP visible. Si se mantiene la descarga remota, que sea HTTPS y con dominios exactos permitidos; para despliegue fiscal es más reproducible empaquetar la fuente. Además, esta solicitud no necesita una ventana principal apuntando al sitio de producción: cargar el renderer local y reservar HTTPS para el backend minimiza contenido remoto privilegiado.
- El cliente de facturación actual manda escrituras que podrían tardar 90 segundos y documenta el caso de timeout con operación completada en servidor. Al pasar a escritorio no se debe reintentar una emisión a ciegas tras cierre, caída o desconexión: mantener un identificador de operación/idempotencia del lado del servidor y consultar estado antes de volver a enviar. Evidencia local: [src/api/http.ts](../../src/api/http.ts), [src/features/expenses/envioDgii.ts](../../src/features/expenses/envioDgii.ts).

### Gaps

- Electron documenta los mecanismos, pero no define una CSP exacta compatible con los estilos, fuentes, imágenes y endpoints de Fiscalo; hay que generarla sobre el renderer real y corregir las violaciones observadas en build instalado.
- No se ha comprobado que `window.open` a Blob, PDF, el diálogo de impresión del navegador o `webContents.print` reproduzcan el flujo de impresora configurada y ticket de 80 mm de Fiscalo. Esta verificación pertenece al prototipo Electron.

## ¿Dónde almacenar preferencias, tokens y credenciales de una app de facturación?

### Takeaway

Dejar preferencias no sensibles en almacenamiento web puede funcionar, siempre que el protocolo local habilite almacenamiento. Sacar tokens y secretos de `localStorage`: la opción Electron para cifrado local es `safeStorage` desde main (preferir API asíncrona), con datos en subcarpeta de `app.getPath('userData')`. `safeStorage` protege el dato en reposo según las capacidades del sistema operativo, pero no es una bóveda universal ni protege frente a código malicioso que ejecute como el usuario.

### Cited Findings

- `safeStorage` cifra/descifra strings usando sistemas de criptografía del sistema operativo. Electron recomienda `encryptStringAsync`/`decryptStringAsync`: no bloquean, soportan rotación de claves y gestionan disponibilidad temporal; la API síncrona puede deprecarse. — [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)
- En Windows, el proveedor DPAPI protege contra otros usuarios del equipo, pero no contra otras aplicaciones ejecutadas bajo el mismo usuario. En macOS se usa Keychain; una firma consistente evita que Keychain trate cada build como una app distinta y pida permiso otra vez después de actualizar. — [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage); [Code Signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)
- En Linux los proveedores pueden ser Secret Service/portal o un backend alternativo según el escritorio. La documentación alerta que `basic_text` equivale a contraseña plaintext codificada y que puede detectarse con `getSelectedStorageBackend()`; la disponibilidad debe evaluarse en runtime, no asumirse. — [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)
- Electron recomienda guardar los datos de la aplicación en una subcarpeta de `app.getPath('userData')`, para evitar colisiones con carpetas internas de Chromium. Ese directorio también puede ser respaldado en algunos entornos; no se recomienda para archivos grandes. Los datos de sesión y `localStorage` viven por defecto en `sessionData`, que apunta a `userData`. — [Electron app API](https://www.electronjs.org/docs/latest/api/app#appgetpathname)
- El almacenamiento cifrado de Electron es específico a la plataforma y se basa en la identidad local. Electron describe `safeStorage` como protección adicional para datos guardados localmente, no como custodia de secretos de servidor o protección contra otras apps del mismo usuario. — [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)

### Inferences

- El store actual de autenticación persiste token Bearer y usuario en `localStorage`; el POS persiste un token de equipo ahí y mantiene token del empleado en memoria. Esto debe entrar en la revisión de seguridad del port: ambos tokens persistentes son credenciales; tema/vista/preferencias de impresora sí son candidatos a almacenamiento no secreto. Evidencia local: [src/stores/auth.ts](../../src/stores/auth.ts), [src/pos/store.ts](../../src/pos/store.ts), [src/stores/impresora.ts](../../src/stores/impresora.ts), [src/App.tsx](../../src/App.tsx).
- Para un destino robusto, el main administra tokens: los cifra con la API asíncrona de `safeStorage` y guarda ciphertext/metadata mínima bajo `userData/fiscalo/`; el bridge no ofrece un `getToken()` que devuelva el secreto al renderer. Lo ideal es que las llamadas autenticadas salgan desde una API del main limitada a operaciones autorizadas y origen HTTPS fijado. Así, el token no vuelve al JavaScript del renderer. Es más trabajo porque hoy `src/api/http.ts` hace `fetch` directamente en React.
- Camino de migración por fases si mover toda la API a main no cabe inicialmente: primero mantener el backend como autoridad y no añadir claves secretas al instalador; corregir almacenamiento persistente para que no use `localStorage`; y planear que el token accesible al renderer sea corto, revocable y de mínimo alcance. Este paso reduce exposición accidental, pero un XSS sigue pudiendo usar/exfiltrar cualquier token disponible en memoria del renderer: context isolation no elimina el riesgo de XSS dentro del renderer.
- Si Linux no tiene proveedor seguro, no persistir credenciales con backend `basic_text`: solicitar nuevo login y mantener la sesión solo en memoria, o tratar ese sistema como no compatible con la persistencia de credenciales. Detectar y explicar el comportamiento evita creer que el token está cifrado cuando no lo está.
- No empaquetar API keys de servidor ni claves privadas de certificado DGII en el frontend o binario: los archivos del ejecutable quedan en manos del usuario y `safeStorage` no es un HSM ni hace que una clave quede imposible de extraer mientras la aplicación la usa. Preferir firma/credenciales del lado servidor si el flujo de negocio lo permite. Si se requiere certificado local, investigar por separado su formato, permisos, importación/rotación y almacén nativo de certificados de cada plataforma.
- Electron documenta la relevancia de firma de código al distribuir, y específicamente que `safeStorage` puede volver a pedir acceso a Keychain tras cada actualización si la firma de macOS no es válida/consistente. Por tanto, firma de instaladores (al menos en Windows/macOS de distribución) forma parte de una ruta estable de almacenamiento, no es solo presentación. — [Electron Code Signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)

### Gaps

- El repositorio frontend no muestra el almacén del certificado DGII ni confirma si la firma de e-CF ocurre en backend. Esta investigación no debe inferir custodia de llaves por el nombre de datos `xml_firmado`.
- No se ha decidido qué sistemas operativos se soportarán. La decisión impacta qué proveedores de `safeStorage` se pueden asumir y qué instaladores, firma y comportamiento de reautenticación se necesitan.
- El esquema de autenticación no detalla vida útil/rotación/revocación de tokens; esa definición es necesaria para evaluar almacenamiento local, sesiones persistentes de POS y recuperación cuando `safeStorage` no esté disponible.
