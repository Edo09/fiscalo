# Distribución de escritorio

## ¿Qué artefactos e instaladores convienen por sistema operativo y qué exigen?

### Takeaway

Electron Forge separa el empaquetado de la app (`package`), la generación de artefactos (`make`) y la publicación (`publish`); `make` puede producir instaladores específicos o archivos ZIP. Para una primera distribución comercial directa, la combinación habitual es instalador Squirrel.Windows para consumidores, DMG más ZIP de actualización en macOS, y paquetes DEB/RPM según el público Linux. La app no se convierte en un único paquete universal: las salidas dependen del sistema operativo y la arquitectura destino. [Forge: build lifecycle](https://www.electronforge.io/core-concepts/build-lifecycle); [Electron: packaging](https://www.electronjs.org/docs/latest/tutorial/tutorial-packaging)

### Cited Findings

- Forge `package` genera un bundle ejecutable y reconstruye complementos nativos para la versión de Electron; `make` convierte ese bundle en un instalador o archivo, y `publish` puede subirlo a GitHub Releases o almacenamiento como S3. Por defecto, `package` y `make` producen el sistema y arquitectura del equipo que ejecuta la compilación. [Forge: build lifecycle](https://www.electronforge.io/core-concepts/build-lifecycle); [Electron: publishing and updating](https://www.electronjs.org/docs/latest/tutorial/tutorial-publishing-updating)
- En Windows, el maker Squirrel.Windows produce `Setup.exe`, un paquete `.nupkg` y un archivo `RELEASES`; su instalador es sin diálogos intrusivos ni privilegios de administrador y es la opción que conecta directamente con el `autoUpdater` nativo de Electron. Para compilarlo se necesita Windows, o Linux con Mono y Wine. Requiere `author` y `description` (o sus equivalentes en configuración Forge). [Forge: Squirrel.Windows](https://www.electronforge.io/config/makers/squirrel.windows); [Electron: autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater/)
- Para despliegue empresarial, Forge puede generar MSI con WiX; su guía recomienda Squirrel en general y describe MSI como formato requerido en algunos entornos empresariales. El maker WiX requiere WiX Toolset v3. Para Microsoft Store o distribución administrada, Forge también dispone de maker MSIX, que requiere Windows 10/11 y Windows SDK; la documentación lo marca experimental. [Forge: WiX MSI](https://www.electronforge.io/config/makers/wix-msi); [Forge: MSIX](https://www.electronforge.io/config/makers/msix)
- En macOS, el DMG es el formato estándar de descarga: presenta la app para copiarla a `/Applications`; Forge solo puede crear el DMG desde macOS. El maker ZIP puede empaquetar el bundle en cualquier sistema de compilación, pero la app dentro sigue siendo para el SO/arquitectura que se empaquetó. [Forge: DMG](https://www.electronforge.io/config/makers/dmg); [Forge: ZIP](https://www.electronforge.io/config/makers/zip); [Forge: build lifecycle](https://www.electronforge.io/core-concepts/build-lifecycle)
- Para Linux, Forge provee DEB para Debian/Ubuntu (Linux o macOS con `fakeroot` y `dpkg`) y RPM para Fedora/RHEL (Linux con `rpm` o `rpm-build`). Flatpak añade aislamiento tipo sandbox y necesita `flatpak`, `flatpak-builder`, `eu-strip` y el runtime de Flathub. [Forge: DEB](https://www.electronforge.io/config/makers/deb); [Forge: RPM](https://www.electronforge.io/config/makers/rpm); [Forge: Flatpak](https://www.electronforge.io/config/makers/flatpak)
- Forge ZIP es un archivo comprimido con la app empaquetada, no un instalador y no un ejecutable portátil Windows de un solo archivo. Electron Forge no documenta un maker oficial `portable` para `.exe`. Como alternativa comunitaria, electron-builder sí documenta un target Windows `portable` de un solo `.exe`, sin instalación, entradas del registro o menú Inicio, pero indica que las actualizaciones son manuales. La documentación oficial de Electron recomienda Forge y clasifica electron-builder como herramienta comunitaria sin soporte oficial del proyecto Electron. [Forge: ZIP](https://www.electronforge.io/config/makers/zip); [electron-builder: targets](https://www.electron.build/v26/docs/targets/); [Electron: Forge overview](https://www.electronjs.org/docs/latest/tutorial/forge-overview)
- La matriz real de release debe incluir un artefacto por OS y arquitectura que se vaya a soportar. Forge permite pasar `--arch`; los manifiestos macOS de ZIP son específicos por arquitectura. Electron recomienda CI para producir versiones de varios sistemas, dado que no siempre se pueden generar los distributables de todas las plataformas en una sola máquina. [Electron: publishing and updating](https://www.electronjs.org/docs/latest/tutorial/tutorial-publishing-updating); [Forge: ZIP](https://www.electronforge.io/config/makers/zip)

### Inferences

- Si la prioridad es una instalación sencilla para usuarios finales y actualizaciones en Windows/macOS, un instalador soportado por el updater da un ciclo de release más integrado que entregar una carpeta o ZIP para ejecución manual. El ejecutable portable de electron-builder reduce fricción al no instalarse, pero el propio selector del proyecto marca sus actualizaciones como manuales. [Forge: Squirrel.Windows](https://www.electronforge.io/config/makers/squirrel.windows); [electron-builder: targets](https://www.electron.build/v26/docs/targets/)
- Para esta app conviene inicialmente limitar la matriz Linux a DEB y RPM solo si hay usuarios de ambas familias. Flatpak y Snap añaden requisitos y canales de distribución propios, así que pueden sumarse cuando exista una necesidad concreta. [Forge: DEB](https://www.electronforge.io/config/makers/deb); [Forge: RPM](https://www.electronforge.io/config/makers/rpm); [Forge: Flatpak](https://www.electronforge.io/config/makers/flatpak)

### Gaps

- No se especificó qué versiones mínimas de Windows, macOS y Linux se soportarán, ni si deben incluirse arquitecturas x64 y ARM64. Eso define las compilaciones y máquinas de CI necesarias.
- No se sabe si clientes empresariales exigen MSI/MSIX, si habrá distribución en tiendas ni si se necesita una descarga sin instalación.

## ¿Qué firma de código y requisitos de release exige la distribución comercial?

### Takeaway

Para la descarga directa comercial, macOS requiere un flujo de firma Developer ID y notarización con Apple; Windows debe firmarse para identificar al editor y reducir los bloqueos de confianza. Linux requiere elegir paquete y canal de distribución, pero Electron no define un equivalente universal de firma de app entre todas las distribuciones. El build debe mantener secretos de firma fuera del repositorio y producir los artefactos desde runners apropiados por plataforma. [Apple: Developer ID](https://developer.apple.com/developer-id/); [Apple: notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution); [Electron: code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)

### Cited Findings

- Apple indica que las apps distribuidas fuera de Mac App Store deben tener certificado Developer ID y recomienda/notariza el software para que Gatekeeper valide su integridad; para notariar se exige firma válida, certificado Developer ID, Hardened Runtime y timestamp seguro. La excepción de notarización es la distribución por Mac App Store. [Apple: Developer ID](https://developer.apple.com/developer-id/); [Apple: notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution?changes=_5)
- Forge implementa firma y notarización macOS en el paso `package` mediante `@electron/osx-sign` y `@electron/notarize`. La guía requiere membresía al Apple Developer Program y Xcode para el flujo de notarización; las credenciales de Apple pueden pasarse desde variables de entorno o un perfil seguro de keychain. [Forge: signing macOS](https://www.electronforge.io/guides/code-signing/code-signing-macos); [Electron: code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)
- La distribución de Mac App Store es un target distinto: Apple Distribution y sandbox/perfil, frente a Developer ID para descarga directa. La guía de Electron dice que las apps firmadas para Mac App Store deben pasar por ese canal para poder ejecutarse. [Electron: Mac App Store guide](https://www.electronjs.org/docs/latest/tutorial/mac-app-store-submission-guide/); [Apple: Developer ID](https://developer.apple.com/developer-id/)
- En Windows, Forge firma instaladores Squirrel.Windows y MSI en el paso `make`; acepta `.pfx` tradicional o `@electron/windows-sign` con Azure Artifact Signing. Los secretos de certificado no deben incluirse en el control de versiones. [Forge: signing Windows](https://www.electronforge.io/guides/code-signing/code-signing-windows); [Electron: code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)
- Hay una diferencia material entre documentación Electron y documentación Microsoft actual: la página de Electron todavía afirma que EV elimina los avisos SmartScreen, pero Microsoft Learn indica que EV dejó de omitir SmartScreen; una app nueva firmada puede aún mostrar advertencia hasta acumular reputación de editor/hash. Microsoft afirma que los paquetes publicados por Microsoft Store no presentan el aviso de descarga SmartScreen. Para predecir el aviso real debe prevalecer la documentación actual de Microsoft sobre el texto antiguo de Electron. [Electron: code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing); [Microsoft: SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- Artifact Signing de Microsoft (antes Trusted Signing) es un servicio administrado que puede integrarse a CI. A la fecha de investigación, los certificados Public Trust están disponibles para organizaciones en EE. UU., Canadá, UE, Reino Unido, Australia, Nueva Zelanda, Japón, Corea del Sur, Singapur, Suiza, Noruega e Israel; las personas desarrolladoras están limitadas a EE. UU. y Canadá. Microsoft describe flujo de validación de identidad, cuenta Azure y perfil de certificado. [Microsoft: Artifact Signing quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart); [Forge: signing Windows](https://www.electronforge.io/guides/code-signing/code-signing-windows)
- Forge publica por GitHub Publisher, S3 u otros publishers. GitHub Publisher requiere permiso de escritura en el repo; en GitHub Actions el `GITHUB_TOKEN` debe tener permisos `contents: write`. La versión del `package.json` determina el nombre de la release GitHub y el publish local normalmente cubre solo el OS/arquitectura anfitrión. [Forge: GitHub publisher](https://www.electronforge.io/config/publishers/github); [Electron: publishing and updating](https://www.electronjs.org/docs/latest/tutorial/tutorial-publishing-updating)

### Inferences

- Para una empresa en República Dominicana, Artifact Signing Public Trust no aparece disponible en la lista vigente de países de Microsoft; si la organización opera desde allí, debe confirmar si otra entidad elegible puede realizar la validación o usar otro proveedor de certificado. La disponibilidad debe revalidarse al iniciar la implementación porque Microsoft administra el servicio y la lista puede cambiar. [Microsoft: Artifact Signing quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)
- Para macOS y Windows, un pipeline de release debería leer secretos de firma desde el almacén de secretos del CI, firmar los outputs apropiados, conservar el mismo identificador de firma y subir únicamente los artefactos finales firmados/notarizados. Esta inferencia sigue los pasos de firma por plataforma y la prohibición explícita de comprometer contraseñas en el repositorio. [Forge: signing macOS](https://www.electronforge.io/guides/code-signing/code-signing-macos); [Forge: signing Windows](https://www.electronforge.io/guides/code-signing/code-signing-windows)

### Gaps

- Falta confirmar si la entidad legal que publicará está en República Dominicana o en otro país y si tiene inscripción empresarial, requisito que afecta elegibilidad de certificados y servicios de firma.
- No se definió si el canal será web, Microsoft Store o Mac App Store; cambia el paquete, la identidad de firma y quién controla las actualizaciones.

## ¿Cómo funcionan las actualizaciones automáticas y qué cambia entre paquete portable e instalador?

### Takeaway

El `autoUpdater` incluido en Electron cubre Windows y macOS, pero no Linux: en Windows su mecanismo depende de Squirrel.Windows o MSIX y macOS exige firma y una carga ZIP compatible. Linux debe actualizarse mediante el canal de paquetes/tienda o con una solución externa. Para una aplicación comercial privada, GitHub `update.electronjs.org` no es el servicio indicado; Forge propone almacenamiento estático o servidor propio. [Electron: autoUpdater API](https://www.electronjs.org/docs/latest/api/auto-updater/); [Electron: updating applications](https://www.electronjs.org/docs/latest/tutorial/updates); [Forge: auto update](https://www.electronforge.io/advanced/auto-update)

### Cited Findings

- Electron `autoUpdater` no tiene soporte Linux integrado y recomienda que Linux se actualice con el package manager de la distribución. En macOS usa Squirrel.Mac y requiere app firmada. En Windows detecta Squirrel.Windows o MSIX y cambia al mecanismo apropiado. [Electron: autoUpdater API](https://www.electronjs.org/docs/latest/api/auto-updater/)
- Para una app macOS distribuida como DMG, Forge pide también generar ZIP: Squirrel.Mac usa el ZIP como payload y puede leer metadatos de actualización por arquitectura desde almacenamiento estático. [Forge: DMG](https://www.electronforge.io/config/makers/dmg); [Forge: ZIP](https://www.electronforge.io/config/makers/zip); [Forge: S3 publisher](https://www.electronforge.io/config/publishers/s3)
- Squirrel.Windows produce los archivos necesarios para actualización (`.nupkg` y `RELEASES`) junto al `Setup.exe`; el `autoUpdater` de Electron lo admite. Squirrel pasa eventos especiales en primera ejecución/actualización/desinstalación, que la app debe manejar para evitar que se abra en momentos inadecuados. [Forge: Squirrel.Windows](https://www.electronforge.io/config/makers/squirrel.windows); [Electron: autoUpdater API](https://www.electronjs.org/docs/latest/api/auto-updater/)
- El servicio gratis `update.electronjs.org` requiere app macOS/Windows con repositorio GitHub público y releases en GitHub; solo exige firma en macOS. Para un repo privado o app comercial, Electron indica que puede ser necesario usar servidor propio; Forge también soporta metadatos de almacenamiento estático como S3. [Electron: updating applications](https://www.electronjs.org/docs/latest/tutorial/updates); [Forge: auto update](https://www.electronforge.io/advanced/auto-update); [Forge: S3 publisher](https://www.electronforge.io/config/publishers/s3)
- electron-builder es una alternativa comunitaria distinta de Forge. Su documentación ofrece `electron-updater`: actualizaciones por NSIS en Windows, DMG en macOS (con ZIP), y AppImage/DEB/Pacman/RPM en Linux; la documentación indica verificación de firma y soporte de metadata de release. No debe confundirse con el updater integrado de Electron: usa el paquete `electron-updater` y su propio formato/configuración. [Electron: Forge overview](https://www.electronjs.org/docs/latest/tutorial/forge-overview); [electron-builder: auto update v26](https://www.electron.build/v26/docs/features/auto-update/)
- El target `portable` de electron-builder genera un solo `.exe` que se ejecuta desde cualquier carpeta y no registra instalación. La misma guía marca las actualizaciones del target como manuales. Forge ZIP produce una carpeta de aplicación comprimida, no ese ejecutable portable. [electron-builder: targets v26](https://www.electron.build/v26/docs/targets/); [Forge: ZIP](https://www.electronforge.io/config/makers/zip)
- Para Linux con electron-builder, los targets AppImage/DEB/RPM pueden usar `electron-updater`, mientras Snap se actualiza por Snap Store; Forge y Electron Core no incluyen updater Linux. La documentación de Forge describe Flatpak como paquete sandbox y DEB/RPM como formatos de cada familia. [electron-builder: auto update v26](https://www.electron.build/v26/docs/features/auto-update/); [Forge: DEB](https://www.electronforge.io/config/makers/deb); [Forge: RPM](https://www.electronforge.io/config/makers/rpm); [Forge: Flatpak](https://www.electronforge.io/config/makers/flatpak)

### Inferences

- Si se elige Forge, la ruta con menos piezas para updates es: Squirrel.Windows para Windows, DMG + ZIP y Squirrel.Mac para macOS, y actualizaciones administradas por repositorio/tienda en Linux. Esto evita desarrollar un actualizador Linux propio, pero depende de cómo se publique el paquete Linux. [Electron: autoUpdater API](https://www.electronjs.org/docs/latest/api/auto-updater/); [Forge: auto update](https://www.electronforge.io/advanced/auto-update)
- Si la prioridad es Windows portable, no hay equivalente de un clic dentro de los makers Forge citados: se acepta actualización manual o se adopta electron-builder con su target `portable`. Si la prioridad es auto-update integral en Windows y Linux, el target NSIS/AppImage/DEB/RPM de electron-builder junto con `electron-updater` cubre más targets, a costa de elegir y mantener un empaquetador/updater alternativo. [Forge: makers](https://www.electronforge.io/config/makers); [electron-builder: targets v26](https://www.electron.build/v26/docs/targets/); [electron-builder: auto update v26](https://www.electron.build/v26/docs/features/auto-update/)
- Una descarga en ZIP o un `.exe` portable reduce pasos de instalación, pero deja al proveedor responsable de comunicar y entregar versiones nuevas; un instalador con updater permite una ruta de actualización integrada y versionada. Para clientes empresariales, MSI/MSIX suele alinearse mejor con política de TI/gestión que el instalador de consumidor. [Forge: Squirrel.Windows](https://www.electronforge.io/config/makers/squirrel.windows); [Forge: WiX MSI](https://www.electronforge.io/config/makers/wix-msi); [electron-builder: targets v26](https://www.electron.build/v26/docs/targets/)

- No se especificó si las actualizaciones deben ser totalmente automáticas, pedir reinicio/confirmación, o quedar en manos de administradores Linux/Windows.
