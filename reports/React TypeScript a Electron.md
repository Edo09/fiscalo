# Convierte Fiscalo en escritorio por etapas

Fiscalo puede convertirse en una aplicación de escritorio con Electron **sin reescribir React ni trasladar el backend**: se conservan los dos renderers actuales y se añade una capa pequeña para ventanas, integración del sistema y empaquetado. El repo usa React 18.3, TypeScript 5.6 y Vite 6; sus scripts son `dev`, `build`, `typecheck`, `lint` y `preview`, y todavía no declara Electron. Su build web renombra `index.html` como `app.html` para el despliegue en Vercel. La ruta recomendada es probar Electron Forge con Vite, conservar separados el build web y el desktop, y cargar los HTML compilados localmente mientras las llamadas de negocio siguen llegando por HTTPS al backend. Antes de convertirlo en instalador hay que resolver cuatro puntos: compatibilidad de versiones, origen/CORS de la API, custodia de tokens y comportamiento real de POS e impresión. ([package.json](../package.json), [vite.config.ts](../vite.config.ts), [Electron Forge Vite plugin](https://www.electronforge.io/config/plugins/vite))

## Conserva React y reutiliza sus dos páginas

La mayor parte del frontend puede quedarse como está: componentes, estilos, formularios, validación TypeScript/Zod, estado y servicios HTTP siguen perteneciendo al renderer web. El proyecto ya configura como entradas `index.html` y `pos.html`; la primera se convierte en `app.html` durante el build web para que Vercel resuelva sus rewrites por host. Esa transformación es específica del despliegue web y debe limitarse a ese build o reflejarse explícitamente en la ruta que cargue Electron. ([vite.config.ts](../vite.config.ts), [index.html](../index.html), [pos.html](../pos.html))

Electron no vuelve local la lógica fiscal: agrega un proceso principal que controla el ciclo de vida y las ventanas, mientras cada `BrowserWindow` ejecuta una página React como renderer. La API actual es remota; el frontend no demuestra dónde se firma el XML ni dónde se guarda el certificado DGII, así que no conviene diseñar una bóveda o un flujo de firma local hasta que backend confirme esa arquitectura. ([Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [src/api/http.ts](../src/api/http.ts))

## Añade main y preload como frontera de escritorio

Añade una capa Electron con `main` para crear la ventana principal y la del POS, registrar el protocolo de la app y manejar operaciones privilegiadas; usa un `preload` pequeño, tipado y conectado con `contextBridge`. El renderer conserva React, pero accede a capacidades de escritorio mediante funciones concretas como abrir POS, guardar un archivo o solicitar impresión. No debe recibir `fs`, `shell`, `ipcRenderer` completo ni un canal IPC genérico. Electron recomienda aislar el contexto, mantener el sandbox, validar el emisor de cada mensaje y limitar navegación y ventanas nuevas. ([Electron security](https://www.electronjs.org/docs/latest/tutorial/security), [context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation), [IPC](https://www.electronjs.org/docs/latest/tutorial/ipc))

Para la ventana instalada, carga recursos incluidos en el paquete; Electron recomienda un protocolo de aplicación propio en lugar de depender de `file://`. Si ese protocolo debe conservar `localStorage`, hay que registrarlo con el atributo `standard`; las rutas de assets del build local también deben ser relativas. Mantener `app.html` y `pos.html` como documentos separados es compatible con la intención actual, pero la combinación concreta de los dos HTML con el plugin Forge debe demostrarse en una build empaquetada: Forge documenta varios renderer targets, mientras Vite documenta entradas multipágina, sin especificar una receta conjunta para este caso. ([Electron protocol API](https://www.electronjs.org/docs/latest/api/protocol/), [Vite multi-page build](https://vite.dev/guide/build#multi-page-app), [Forge Vite plugin](https://www.electronforge.io/config/plugins/vite))

## Fija Forge y Vite antes de migrar el build

Electron Forge con `@electron-forge/plugin-vite` es la opción que mejor encaja con el stack: separa los builds de main, preload y renderer, y puede arrancar el renderer desde Vite durante desarrollo. Sin embargo, el repo está en Vite 6 y la versión Forge 8.0.1 consultada actualizó su plugin a Vite 8 y lo graduó fuera de experimental. A la vez, la página de documentación del plugin aún conserva el aviso de experimental de Forge 7.5.0. Por esa discrepancia, fija primero una pareja de versiones compatible y comprueba la ayuda del CLI de esa versión; no copies al repo la plantilla o el comando antiguo sin verificarlo. Forge 8 también actualizó sus plantillas a Node 22 y ESM. ([Forge 8.0.1 release](https://github.com/electron/forge/releases/tag/v8.0.1), [Forge Vite plugin docs](https://www.electronforge.io/config/plugins/vite), [unificación de plantillas Forge](https://github.com/electron/forge/pull/4229))

Mantén el script actual de build web para Vercel y configura una compilación renderer de escritorio sin aplicar por accidente el plugin `appHtmlSinIndex`: hoy corre en todo build de Vite y elimina `index.html`. En desktop, el proceso main debe cargar el nombre HTML producido realmente para cada ventana. También revisa `base` y las URLs de recursos para que funcionen desde el origen local y no dependan de rutas absolutas como `/assets/...`. ([vite.config.ts](../vite.config.ts), [Forge Vite plugin: rutas del renderer](https://www.electronforge.io/config/plugins/vite), [Vite build options](https://vite.dev/config/build-options.html))

El proxy `/api` del repo vive solo en el servidor de desarrollo de Vite. Un ejecutable instalado no lo tendrá: `src/api/config.ts` deja la base vacía si no se define `VITE_API_BASE_URL`, y `src/api/http.ts` llama `fetch` directamente desde el renderer. El build desktop debe definir el endpoint HTTPS de producción y contemplar su nuevo origen local —por ejemplo, un esquema `app://`— en la política CORS del backend. Si CORS no puede aceptar de forma segura ese origen, la alternativa es mover llamadas seleccionadas a handlers del proceso main y exponer resultados tipados por IPC; no debe tratarse el proxy de Vite como parte del producto instalado. ([vite.config.ts](../vite.config.ts), [src/api/config.ts](../src/api/config.ts), [src/api/http.ts](../src/api/http.ts), [Electron security](https://www.electronjs.org/docs/latest/tutorial/security))

## Rediseña credenciales, POS e impresión con cautela

Hoy el token de la sesión principal y el token persistente del equipo POS se guardan en `localStorage`; la sesión del empleado POS queda en memoria. También existe `VITE_API_KEY`, que el código describe como incluida en el bundle si se usa en producción. **No incluyas una clave de servidor en el renderer ni en el instalador**: el usuario controla el equipo y puede inspeccionar el paquete. Para credenciales de usuario que deban persistir, Electron `safeStorage` permite cifrado mediante el sistema operativo y recomienda su API asíncrona, pero no protege frente a otros procesos ejecutados por el mismo usuario; en Linux hay que detectar el backend disponible y no asumir que siempre cifra. Si el token queda accesible al renderer, una vulnerabilidad XSS aún puede usarlo. ([src/api/config.ts](../src/api/config.ts), [src/stores/auth.ts](../src/stores/auth.ts), [src/pos/store.ts](../src/pos/store.ts), [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage))

El botón POS pide un código de handoff de un solo uso y abre una pestaña web con `#code=...`; en desktop, el main debería abrir el HTML local `pos.html` con ese fragmento después de recibir el código por una operación tipada del preload. El backend debe confirmar que el intercambio del código funciona desde la app empaquetada y con su origen nuevo. La impresión actual usa iframes, `window.print`, blobs y descargas; se puede conectar a APIs de impresión/guardado de Electron, pero primero hay que comprobar el papel de 80 mm, los saltos de página, el diálogo de impresora y la salida de PDF/XML en los equipos reales. ([src/components/layout/Navbar.tsx](../src/components/layout/Navbar.tsx), [src/lib/printHtml.ts](../src/lib/printHtml.ts), [src/lib/file.ts](../src/lib/file.ts), [webContents.print](https://www.electronjs.org/docs/latest/api/web-contents/#contentsprintoptions-callback))

## Deja instaladores y actualizaciones para una segunda fase

Primero valida en una máquina el arranque de ambas ventanas, build empaquetado, API/CORS, login, POS, impresión y descargas. Luego decide sistemas operativos, arquitecturas, si será instalador o descarga portable, y cómo llegarán actualizaciones. En Forge, `package` arma el bundle para una plataforma y `make` produce los instaladores configurados; por defecto el resultado depende del sistema y arquitectura de build, por lo que una distribución multiplataforma requiere planear runners y firma por sistema. ([Forge build lifecycle](https://www.electronforge.io/core-concepts/build-lifecycle), [Electron packaging](https://www.electronjs.org/docs/latest/tutorial/tutorial-packaging))

## Conclusión

La decisión práctica es construir primero una shell Electron delgada sobre los renderers actuales y conservar al backend como autoridad para emisión, numeración fiscal y estado DGII. Antes de ampliar el piloto, producto y backend deben confirmar el dominio HTTPS y CORS admitido, el ciclo de vida de los tokens, el origen permitido para el handoff del POS y dónde se firma el certificado DGII. El prototipo también debe demostrar impresión térmica de 80 mm y que el build web de Vercel siga produciendo sus nombres de archivo esperados; solo entonces se debe fijar la matriz de instaladores y actualizaciones.
